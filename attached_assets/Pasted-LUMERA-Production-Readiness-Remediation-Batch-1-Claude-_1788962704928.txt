F1 — REVOKE SESSIONS AFTER OWNER PASSWORD RESET
--------------------------------------------------

Claude finding:

POST /salon/employees/:employeeId/access/reset-password

updates the employee password and sets mustChangePassword=true,
but does not revoke the employee's existing sessions.

Existing sibling flows already revoke sessions, including employee
deactivation and password-change/setup flows.

Required behavior:

When a salon owner successfully resets an employee password:

- update the password exactly as today
- preserve mustChangePassword behavior
- revoke ALL existing sessions belonging to that employee
- perform password update and session revocation atomically
- if any part fails, rollback the entire operation

Do not change unrelated authentication/session behavior.

Regression test:

1. Authenticate employee.
2. Capture valid employee session.
3. Owner resets employee password.
4. Attempt an authenticated employee request using the OLD session.
5. It must return 401.
6. It must NOT merely return 428 because mustChangePassword changed.
7. Verify new login/setup behavior still works correctly.

--------------------------------------------------
F2 — TRANSACTIONAL CANCELLATION EMAIL OUTBOX
--------------------------------------------------

Claude finding:

The appointment cancellation state commits before the cancellation
email is inserted into email_deliveries.

sendAppointmentEmails is called without the transaction store after
the cancellation transaction has already completed.

This violates the transactional-outbox invariant already documented
in the codebase.

Required behavior:

The appointment cancellation state change and creation of its
transactional email outbox record must share the same transaction.

If the transaction commits:
- both cancellation and required outbox row exist.

If the transaction rolls back:
- neither exists.

Do NOT send the external email synchronously inside the booking
transaction.

Only enqueue the durable outbox record transactionally.

Actual external provider delivery must remain asynchronous.

Preserve:
- cancellation behavior
- authorization
- locking
- booking availability release
- notifications
- SMS behavior
- existing retry/idempotency behavior

Add a regression/fault-injection test proving that there is no
commit boundary where the appointment is cancelled but its required
email outbox row does not exist.

Claude identified an unfiltered:

IMPORTANT:

Do NOT change +381 behavior in this task.

Do NOT alter contact identity/merge semantics beyond removing the
full-table scan.

Inspect the actual query patterns and existing schema first.

If the required lookup column does not have an appropriate index,
add the smallest appropriate index using the project's established
schema conventions.

Do not add speculative indexes.

Regression tests must prove:

- matching contacts are still found correctly
- unrelated contacts are not loaded
- existing Serbian contact-linking behavior remains unchanged
- query work remains bounded as unrelated salonCustomers rows grow
- tenant/data-integrity behavior is unchanged

A-6 — MAXIMUM BOOKING HORIZON
--------------------------------------------------

Claude found that minimum lead time exists but there is no maximum
future booking horizon.

Implement this using the existing salon booking-settings architecture
rather than a hardcoded route-level workaround.

Requirements:

- salon can have a maximum future booking horizon
- server is authoritative
- availability must not advertise slots beyond the horizon
- direct/manual/API attempts beyond the allowed horizon must also
  be rejected server-side
- boundary at the last valid time/date must be tested
- preserve existing bookings already stored beyond a newly reduced
  horizon
- do not silently cancel or modify historical/existing appointments
- use the same central availability/booking logic for all entry
  points

Choose a safe backwards-compatible default that preserves existing
behavior for salons that have not configured this setting.

Do not introduce a breaking migration/default that suddenly prevents
currently valid booking behavior.
