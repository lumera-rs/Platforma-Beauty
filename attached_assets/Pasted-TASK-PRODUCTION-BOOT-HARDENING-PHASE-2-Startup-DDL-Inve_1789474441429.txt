==================================================
BACKGROUND
==================================================

Independent audits previously found that normal API startup executes
multiple schema/DDL routines before the server begins listening.

The previous audit identified approximately eight startup schema routines,
plus other post-listen maintenance behavior.

It also found:

- there is currently no complete executable versioned migration history;
- startup ensure routines are effectively acting as a schema authority;
- Replit Publish may independently apply a schema diff;
- therefore there are competing schema authorities;
- startup DDL cannot safely be removed until baseline/adoption/migration
  ownership exists;
- some schema objects such as triggers, pg_trgm-dependent structures,
  constraint validation state and cleanup structures may currently only
  be owned by startup routines;
- media schema DDL has additional locking/concurrency concerns;
- DB query/statement timeout is approximately 30 seconds.

DO NOT TRUST THESE statements blindly.

Reconstruct the CURRENT repository state before implementing anything.

==================================================
E. ANTI-WEAKENING RULES
==================================================

Design the guard so a developer cannot trivially bypass it by:

- renaming ensureSomethingSchema();
- moving SQL into another local module;
- barrel re-export;
- literal dynamic import;
- require();
- wrapping SQL in a helper;
- adding a new startup call;
- adding a new DDL-capable module to index.ts.

Non-literal dynamic imports in the production startup graph must be treated
conservatively and reported.

Do not add a generic option equivalent to:

disableStartupDdlGuard: true

Do not create an allow-all escape hatch.

If an explicit baseline entry is required, it must be narrow and visible.

==================================================
F. REPORT-ONLY VS ENFORCED BEHAVIOR
==================================================

Phase 2 guard must enforce:

NEW / UNEXPECTED startup DDL → TEST FAILURE.

But it must temporarily allow:

EXACT CURRENT REVIEWED STARTUP DDL BASELINE → PASS.

This lets CI/publish stay green today while preventing the problem from
growing.

Later phases will shrink this baseline to zero as DDL ownership moves to
the migration system.

The guard should therefore report something like:

Known startup DDL owners: N
Unexpected startup DDL owners: 0
Missing expected owners: 0
Result: PASS

If a known owner disappears in a future phase, that should be detectable so
we can deliberately update/shrink the baseline rather than silently drift.
