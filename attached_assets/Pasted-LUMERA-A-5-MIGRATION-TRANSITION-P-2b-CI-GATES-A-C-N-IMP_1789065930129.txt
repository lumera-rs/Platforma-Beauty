==================================================
OBJECTIVE
==================================================

Implement the first CI enforcement layer for the Lumera migration system.

Required gates:

A. migration directory/header contract validation

B. immutable migration checksum/history protection

C. migration sequence integrity:
   - duplicate IDs
   - gaps
   - malformed ordering/layout

N. CI must not accidentally access a production/shared database.

This task must make the migration contract enforceable in CI without
creating any ability to execute migrations.

==================================================
1. INSPECT EXISTING CI FIRST
==================================================

Before changing anything, inspect:

.github/workflows/ci.yml

and all scripts currently used by the CI/release chain.

Determine:

- existing jobs
- existing DATABASE_URL behavior
- PostgreSQL service usage
- migration-contract scripts already exposed in package.json
- protected-reference / immutable-history checking mechanism
- whether a migration-contract CI command already exists

Reuse existing patterns.

Do not create duplicate CI systems.

==================================================
2. GATE A — CONTRACT VALIDATION
==================================================

CI must validate the complete migration contract.

This includes all P.1a + P.2a rules:

- migration directory naming
- six-digit IDs
- sequence rules
- exactly one regular migration.sql
- no sidecars
- no symlinks
- directive header grammar
- required directives
- unknown directives rejected
- duplicate singleton directives rejected
- migration ID matches directory
- PostgreSQL version range validation
- migration mode validation
- SQL body non-empty under current P.2a semantics
- full-file checksum generation

Use the existing migration-contract implementation.

DO NOT duplicate this validation logic inside YAML.

CI should call one authoritative repository script.

==================================================
3. GATE B — IMMUTABLE HISTORY
==================================================

CI must detect modification of migration history that already exists on
the protected reference branch.

Examples that must fail:

- editing an existing migration.sql
- changing its header
- changing SQL body
- changing LF ↔ CRLF
- renaming an existing migration directory
- deleting a migration
- replacing an old migration with different contents
- reusing an already-existing migration ID

The entire migration.sql byte stream is checksummed.

The existing P.1a immutable-history comparison must remain the authority.

Do NOT create another checksum implementation.

==================================================
4. REFERENCE BASELINE
==================================================

CI history comparison must use a trustworthy protected repository
reference.

Determine the correct reference in the existing GitHub workflow.

Prefer the target/base branch checkout or another existing trusted
reference model.

Do NOT:

- compare only against the current working tree
- let the PR author provide an arbitrary reference directory
- generate a reference from the changed migration files
- create a manifest that self-authorizes modified history

Fail closed if the trusted reference cannot be established where
history comparison is required.

For the current state where no real migrations exist yet, ensure the
logic still behaves correctly.

==================================================
5. GATE C — SEQUENCE INTEGRITY
==================================================

CI must reject:

- duplicate IDs
- missing sequence numbers
- malformed migration directory names
- invalid sequence start
- migration directories that violate the P.1a contract

Current architecture:

future forward migrations start:

000001
000002
000003
...

000000 is reserved for the future baseline design and is NOT being
created in P.2b.

Do NOT create 000000 now.

Do NOT alter sequence semantics prematurely unless required by the
already-approved P.2 architecture.

If supporting future 000000 requires later contract work, explicitly
defer it to the baseline task rather than weakening current P.1a.

==================================================
6. GATE N — NO SHARED / PRODUCTION DB ACCESS
==================================================

This is critical.

P.2b itself does not require PostgreSQL.

Migration-contract CI must execute without DB access.

For the migration-contract CI step/job:

- DATABASE_URL should be absent or explicitly empty
- LUMERA_MIGRATION_DATABASE_URL should be absent
- no production DB secret should be exposed
- no staging/shared development DB secret should be exposed
- no fallback to application DATABASE_URL
- no pg service container is needed for this gate

Fail closed if the migration-contract tooling unexpectedly attempts DB
access.

Use the repository's existing pattern if CI already sets:

DATABASE_URL: ""

Do not introduce actual database credentials.

10. PULL REQUEST VS MAIN BRANCH BEHAVIOR
==================================================

Design the workflow carefully.

For pull requests:

- compare migration history against the trusted PR base revision

For pushes to the protected branch:

- validate the current complete migration set
- do not create a false failure because the merge itself is now the
  reference

If immutable-history comparison needs different behavior for PR vs push,
implement that explicitly and test it.

Do not silently skip Gate B on PRs.

11. SHALLOW CHECKOUT / GIT HISTORY
==================================================

Prefer exact base-SHA retrieval where possible.

Do not rely on a branch name that can race or move during the job if an
immutable SHA is available.
