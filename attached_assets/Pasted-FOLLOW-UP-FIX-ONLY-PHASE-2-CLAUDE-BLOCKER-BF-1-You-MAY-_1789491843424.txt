==================================================
BLOCKER BF-1
==================================================

File:

scripts/src/production-startup-ddl-inventory.ts

Claude found that scanTopLevelModule() detects direct top-level SQL sink
calls but does NOT follow indirect executable calls during module evaluation.

This creates false negatives for DDL executed at module-import time.

Examples currently MISSED by the guard:

1. top-level:
   boot();

   where boot() executes DDL

2. top-level IIFE:
   (() => {
     // DDL
   })();

3. top-level:
   new Bootstrapper();

   where constructor executes DDL

4. top-level call into another imported module

5. top-level:
   Promise.resolve().then(callbackContainingDdl)

6. two or more static module hops followed by a top-level executable call

7. similar executable module-evaluation indirection

Module evaluation is production startup behavior and occurs pre-listen.

Therefore startup DDL reached through these paths MUST be inventoried and
baseline-checked.

==================================================
IMPORTANT CALLBACK SEMANTICS
==================================================

Be careful not to create false positives by treating every callback passed
during module evaluation as immediately executed.

Distinguish callbacks that can execute as part of startup/module evaluation
from callbacks that are merely registered for later execution.

For example:

- Promise.then(...) attached during module evaluation can execute as part
  of startup/module evaluation and must be conservatively analyzed.

But do NOT incorrectly classify unrelated request handlers or permanently
registered callbacks as immediate pre-listen DDL merely because a function
value appears as an argument.

If the existing analyzer intentionally handles these conservatively,
preserve its existing semantic model and document it.
