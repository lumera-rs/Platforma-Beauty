1. A-2a — EMPTY NORMALIZED PHONE REGRESSION
==================================================

Claude confirmed that the new generated phone lookup implementation
maps NULL/empty/digit-free phone values to an empty string.

POST /salon/appointments currently calls:

normalizedPhone(parsed.data.guest!.phone)

and then findSalonCustomerByPhone(...)

without rejecting an empty normalized value.

This can cause a digit-free placeholder phone to match an arbitrary
phoneless CRM contact and potentially attach/reassign appointments
to the wrong customer.

This is a confirmed Batch 1 regression.

Required behavior:

- An empty normalized phone must NEVER be used for contact matching.
- Digit-free input must not match an existing phoneless contact.
- Preserve existing Serbia +381 behavior.
- Preserve valid contact-linking semantics.
- Preserve tenant isolation.

Use the same central validation behavior consistently across all
relevant booking/contact entry points.

Prefer making invalid/digit-free phone input fail validation with an
appropriate 4xx response rather than silently linking it.

Also inspect whether the generated lookup expression should return
NULL rather than '' for a phone that contains no digits.

If the generated column is removed as part of item 2 below, ensure
the replacement expression has equivalent safe NULL semantics.

Regression test required:

Create at least one existing phoneless CRM contact.

Submit a booking with a digit-free/invalid guest phone.

Prove that:
- it does not match the phoneless contact
- it does not mutate that contact
- it does not reassign its appointments
- the request is rejected appropriately

Also preserve tests for valid:
- local Serbian phone
- +381
- 00381
