==================================================

==================================================

The ledger itself must be created safely and idempotently.

Do not silently overwrite:

- an existing migration row;
- a checksum;
- a failed state;
- an applying/interrupted state.

If the same migration ID exists with a different checksum:

FAIL CLOSED.

If an unknown migration exists ahead of the binary's manifest:

FAIL CLOSED.

Do not automatically repair migration history.

==================================================
11. MIGRATION RUNNER
==================================================

Implement a migration runner that is callable EXPLICITLY.

It must NOT be invoked automatically by production application startup.

The runner must:

1. obtain a bounded global migration lock;
2. read/initialize the ledger;
3. validate manifest vs ledger;
4. validate checksums;
5. determine current frontier;
6. apply only the next valid migrations in order;
7. persist state transitions;
8. release lock/client safely;
9. fail closed on inconsistency.

No concurrent runners may apply the same migration twice.

==================================================
12. BOUNDED LOCKING
==================================================

Use a stable migration advisory lock or equivalent repository-approved
locking mechanism.

No unbounded wait.

Use explicit lock/statement timeout behavior.

Do NOT reuse hashtext-based locking blindly if a safer stable key mechanism
already exists or can be defined explicitly.

The runner must fail safely when it cannot acquire the lock.

13. TRANSACTIONAL MIGRATIONS
==================================================

BEGIN
→ ledger APPLYING as appropriate
→ migration SQL
→ ledger APPLIED
→ COMMIT

or another transactionally equivalent design.

migration falsely APPLIED.

Test this.

==================================================
14. NON-TRANSACTIONAL MIGRATIONS
==================================================

The design must support future operations that cannot run inside a normal
transaction, e.g. CREATE INDEX CONCURRENTLY.

For NON_TRANSACTIONAL migrations:

- record durable APPLYING state before execution;
- execute outside transaction as required;
- mark APPLIED only after successful completion.

CRITICAL:

the next runner invocation MUST NOT blindly rerun it.

It must HALT with an explicit interrupted/non-transactional recovery state.

No automatic guess that the migration completed.

Manual/operator reconciliation belongs to a later explicit workflow.
