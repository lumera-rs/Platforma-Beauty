==================================================
OBJECTIVE
==================================================

Extend the existing P.1a migration contract so migration.sql can contain
a machine-readable Lumera directive header.

The header must be strictly parsed and validated BEFORE any future DB
connection or execution can occur.

The migration file remains the single authoritative artifact.

Checksum remains SHA-256 of the ENTIRE migration.sql byte stream,
INCLUDING the header.

==================================================
TARGET HEADER FORMAT
==================================================

Design and implement support for this logical format:

-- lumera:migration-format 1
-- lumera:id 000001
-- lumera:mode transactional
-- lumera:description Reward-gift lines may never carry a bundle.
-- lumera:min-postgres 16
-- lumera:max-postgres 16
-- lumera:precondition-sql SELECT ...
-- lumera:postcondition-sql SELECT ...
-- lumera:recovery Drop the NOT VALID constraint and re-run.
-- lumera:end-header

<SQL body>

Do NOT blindly implement exactly this text without checking the existing
contract style and parser conventions.

Preserve the architecture, but choose the smallest compatible
implementation.

==================================================
VALIDATION RULES
==================================================

1. Header must appear at the very beginning of migration.sql.

Allow only harmless file-start trivia if absolutely necessary because of
existing UTF-8/BOM handling. Prefer exact start.

2. Header terminates only at:

-- lumera:end-header

3. No directive may appear after end-header.

4. Unknown lumera:* directive:
FAIL CLOSED.

5. Duplicate singleton directive:
FAIL CLOSED.

6. Repeatable precondition/postcondition directives:
allowed.

7. Missing required directive:
FAIL CLOSED.

8. lumera:migration-format:
currently exactly 1.

Unknown future format:
FAIL CLOSED.

9. lumera:id:
must exactly equal the six-digit directory migration ID.

Example:

directory:
000017_add_booking_guard/

header:
-- lumera:id 000017

Any mismatch:
FAIL CLOSED.

10. lumera:mode:

allowed exactly:

transactional
nontransactional

Do not accept aliases.

11. lumera:description:

- required
- non-empty after trimming
- one logical line only
- reasonable bounded length
- no control characters

Do not over-engineer prose validation.

12. min-postgres / max-postgres:

- integers
- currently must support PostgreSQL 16
- min <= max
- reject invalid/unsupported ranges

Integrate with the repository's existing supported PostgreSQL-major
constant if one already exists.

Do not create duplicate PostgreSQL-version authorities.

13. recovery:

- required
- non-empty
- descriptive free text
- bounded length
- not executable

14. SQL body:

must not be empty after the header.

P.2a does NOT validate whether body SQL is transactional-safe or
nontransactional-safe.

That belongs to a later runner task.

15. precondition-sql and postcondition-sql:

P.2a should parse and retain them.

If the existing read-only SQL validator can be reused safely without
dragging DB/runtime dependencies into this module, validate that they are
read-only SELECT/WITH statements.

If that would create coupling or scope expansion, only perform
syntax/shape storage now and explicitly defer execution/read-only
enforcement to P.2e/P.2g.

Do NOT implement a half-safe SQL executor.

==================================================
