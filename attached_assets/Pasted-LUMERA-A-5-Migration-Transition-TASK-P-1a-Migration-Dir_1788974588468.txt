==================================================
1. MIGRATION DIRECTORY CONTRACT
==================================================

Create the directory contract:

lib/db/migrations/

Future real migrations will use:

000001_<snake_case_purpose>/
  migration.sql

000002_<snake_case_purpose>/
  migration.sql

etc.

Rules:

- exactly six numeric digits
- starts at 000001
- strictly monotonic
- no gaps
- no duplicate sequence numbers
- sequence number never reused
- lowercase snake_case purpose
- meaningful purpose
- no dates
- no branch names
- no task numbers
- no generic names such as:
  fix
  final
  final_fix
  v2
  new
  update
  changes

Do NOT create a real migration yet.

Do NOT create baseline SQL.

Fixtures must live outside the real migration directory or otherwise
be unmistakably test-only.

==================================================
2. STATIC VERIFIER
==================================================

Implement a verifier under:

scripts/src/migration-contract/

It must inspect the migration filesystem only.

It must NOT:

- import pg
- import postgres clients
- read DATABASE_URL
- access network
- execute SQL
- inspect live DB
- invoke drizzle-kit push
- invoke bootstrap
- mutate migration files

Verifier must fail closed for:

- invalid directory name
- duplicate sequence
- missing sequence/gap
- non-monotonic ordering
- reused sequence
- missing migration.sql
- unexpected migration structure
- invalid generic purpose
- date-like purpose
- branch/task-like purpose

==================================================
3. IMMUTABILITY / SHA-256
==================================================

Implement SHA-256 verification for historical migrations.

Goal:

Once a migration exists in the protected reference history,
its execution-relevant contents may never silently change.

Verifier must detect:

- edited migration.sql
- renamed migration directory
- removed historical migration
- replaced migration
- sequence reuse

Do not invent a second migration ordering authority.

For this task, implement the smallest mechanism needed to compare the
current migration set against a protected/reference migration set.

Prefer Git/main history comparison if it can be done deterministically
without network access.

Do NOT require GitHub API/network access.

If main/reference history is unavailable locally, fail explicitly or
provide a clearly-defined CI reference input rather than silently
passing.

Document exactly how the reference set is selected.
